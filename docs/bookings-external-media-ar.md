# تحويل وسائط الحجوزات إلى Cloudinary وR2

التنفيذ خاص بفرع `feature/bookings`، انطلاقًا من `2d7b4605508dbf4c94eb03b5cb5093480d7fe004`. لم يُنشر Firebase أو Worker أو تطبيق إنتاج، ولم تتغير الفوترة. أسرار الخدمات لم تُقرأ أو تُنسخ إلى العميل. جاهزية الكود والاختبارات المحلية لا تعني جاهزية الخدمات الخارجية للتشغيل.

## المسارات الجديدة

- صور الأماكن والشاليهات والقاعات والمزارع وبنرات الحجوزات: `uploadBookingImage` يستقبل صورة base64، يفحص الحجم والتوقيع الأولي للملف، ويحجز الحصة ذريًا. Cloudinary يعيد تحليل الصورة في خدمة الرفع. يرفع الخادم بمعرّف ثابت فريد، `overwrite=false` و`type=authenticated`، ويحفظ `public_id` و`resource_type` والنوع والحجم والنسخة والصيغة. لا توجد أسرار أو توقيعات رفع في Flutter ولا استخدام لـunsigned preset للحجوزات.
- الصور تُعرض عبر `bookingImage` الذي يجلب البايتات من Cloudinary بعد فحص الصلاحية، دون كشف رابط Cloudinary الموقّع. القراءة العامة تتطلب الموافقة ومكانًا نشطًا ومالكًا غير محظور وملكية مطابقة. المالك الحالي والمراجع الإداري يستطيعان معاينة الصور قيد المراجعة. الاستجابة `private, no-store`.
- الفيديو: `reserveBookingVideo` يحجز سجلًا وحصة. Flutter يرسل Firebase ID token والبايتات إلى `/bookings/upload?mediaId=...`. Worker يستدعي `bookingVideoBridge` بسر مشترك؛ Firebase Admin يتحقق من المشروع والانتهاء والإلغاء وحالة الحساب وعدم كونه مجهولًا والملكية الحالية. المطالبة بالحجز أحادية الاستخدام. لا يقبل العميل key أو URL أو ownerUid من اختياره.
- Worker يفحص `video/mp4` وتوقيع `ftyp` والحجم المستلم فعليًا، مع مهلة خمس دقائق. `FixedLengthStream` يمرّر الفيديو إلى R2 دون تجميعه كاملًا في ذاكرة Worker. الحد 50MiB. هذا تحقق من الحاوية، وليس فحص برمجيات خبيثة أو ضمانًا لكل codecs.
- `BOOKINGS_BUCKET` يجب أن يكون خاصًا ومستقلًا عن حاوية الريلز؛ المفاتيح `bookings/venues/{venueId}/{ownerUid}/{mediaId}.mp4`. العرض `/bookings/media/{mediaId}.mp4` يعيد فحص الموافقة والنشاط أو صلاحية المالك/الإدارة، ويدعم Range وHEAD.
- الموافقة على ملفات المكان إدارية مستقلة عن المالك. `reviewBookingExternalMedia` ينشر المرجع داخل `mediaPaths`. الرفض ينقل الملف إلى قائمة الحذف. واجهة المالك تعرض الملفات غير المنشورة وحالة المراجعة وتسمح بإزالتها.
- `ownerUid` و`ownerId` متطابقان في السجلات الجديدة للتوافق مع القواعد والواجهات القديمة. `schemaVersion=2` و`kind=venue|banner` يميّزان السجلات. بنر المكان يحمل venueId الوجهة؛ البنر الخارجي يستخدم مساحة `banners`. تغيير وجهة بنر بين أماكن مختلفة يحتاج صورة جديدة مخصصة للوجهة الجديدة.

## الحصص ودورة الحذف

الحد 20 ملفًا منشورًا لكل مكان، و30 سجلًا غير محذوف لوسائط المكان بما فيها الطلبات قيد الرفع والمراجعة والحذف. البنرات لها سقف 200 سجل ضمن مساحة الوجهة. سقف كل مستخدم في يوم UTC هو 100 محاولة و500MiB، والطلبات الفاشلة لا تعيد الحصة اليومية لمنع إساءة إعادة المحاولة. الصور 10MiB والفيديوهات 50MiB. حجز الحصة والمطالبة بالرفع يستخدمان معاملات Firestore لمنع تجاوز الحصص بالتزامن.

إزالة المرجع وحالة المراجعة تحدث ذريًا قبل الحذف الفعلي. الملفات التي دخلت `delete_pending` لا تعود إلى الموافقة. الحذف الفعلي مؤجل إلى `cleanupBookingExternalMedia` كل ساعة؛ فشل الخدمة يبقي الحالة ويزيد attempts ويحفظ سببًا عامًا ويستخدم تراجعًا زمنيًا حتى 24 ساعة. لا تُسجَّل الأسرار أو استجابات الخدمات الحساسة. الصور المستبدلة والمحذوفة من البنرات الجديدة تدخل القائمة نفسها.

قبل الحذف تُفحص مراجع الأماكن والبنرات ومراجعات الوسائط والريلز، وكذلك روابط العقارات والبنرات الأصلية. Cloudinary يقبل فقط المعرف والصنف المتوقعين في مساحة الحجوزات. Worker لا يقبل حذفًا من عميل Firebase؛ يحتاج السر المشترك وموافقة جسر الخادم على حالة الملف ومفتاحه وعدم وجود مراجع. مفاتيح `reels/` تُرفض. الحذف idempotent عند غياب الملف.

الرفع غير المكتمل والصور المرفوعة لبنر لم يُحفظ تُنظّف بعد 24 ساعة. ملفات المكان `pending` لا تُحذف تلقائيًا بسبب انتظار المراجعة. إلغاء رفع ما زال جاريًا يؤجل الحذف حتى انقضاء مهلة الاحتفاظ لتجنب سباق حذف ملف قبل انتهاء كتابته. فشل التأكيد بعد R2 put يبقي سجل الحجز للمتابعة؛ لا يحذف Worker عشوائيًا بعد استجابة خادم غير مؤكدة.

السجل `booking_legacy_media_deletions` مخصص للحذف الصريح لملف Firebase قديم فقط، ويعيد محاولة حذف الخادم بعد فحص المراجع. لا يسمح العميل بكتابة هذه السجلات. سجلات `booking_legacy_media_retained` تحفظ روابط بنرات Firebase القديمة المستبدلة أو المحذوفة لتدقيق انتقال يدوي لاحق.

## البيانات القديمة وخطة الانتقال

1. أنشئ نسخة احتياطية وجردًا للوثائق والملفات والمراجع على بيئة اختبار منفصلة أولًا، وحدد الملفات القديمة بالمسارات `booking_media/...` وروابط بنرات Firebase. لا تستخدم هذا الفرع لنشر الإنتاج دون موافقة.
2. جهّز الأسرار والروابط وحاوية الفيديو الخاصة على الاختبار، ثم اختبر رفعًا حقيقيًا وصورة وفيديو ومراجعة وحذفًا وإعادة محاولة فشل، وحالات الحساب المحظور ونقل الملكية والأجهزة المستهدفة.
3. انشر وظائف الاختبار وWorker الاختبار والفهارس والقواعد، ثم نسخة Flutter الاختبار. تغييرات Storage تمنع إنشاء ملفات حجوزات وبنرات جديدة في المسارات القديمة؛ تبقى قواعد قراءة الملفات القديمة كما هي. التطبيقات القديمة لن تستطيع رفع وسائط حجوزات بعد تطبيق هذه القواعد. نسّق التفعيل مع إصدار التطبيق أو اعمل نافذة انتقال قبل تعطيل الرفع القديم؛ لا توجد إعادة توجيه صامتة إلى خدمة غير مهيّأة.
4. `mediaPaths` القديمة تبقى وتُعرض بـFirebase Storage: الصور `getData` والفيديو `getDownloadURL`. الروابط الجديدة HTTPS تمر إلى بوابات الخادم. وثائق الملكية وإيصالات الحجز تبقى على Firebase Storage كما كانت.
5. لا ترحيل أو حذف جماعي تلقائي. النسخ الاختياري لاحقًا يحتاج خريطة old path → new mediaId، وتحققًا من الحجم والمحتوى والمراجع وصلاحية المالك والموافقة، ثم تحديثًا ذريًا للمراجع بعد اختبار العرض. احتفظ بالنسخة القديمة فترة مراجعة يحددها المشغّل.
6. الملفات القديمة ذات روابط تنزيل Firebase قد تبقى قابلة للوصول لمن يملك رابط التنزيل حتى حذف الملف الصريح؛ القواعد الجديدة لا تلغي رابطًا صادرًا مسبقًا. الصور الجديدة لا تكشف رابط التخزين، والفيديو الجديد لا يُخزن في حاوية عامة. نقل ملكية مكان يمنع القراءة العامة لوسائط v2 المرتبطة بالمالك السابق؛ على الإدارة معالجة مراجعها ورفع أو اعتماد وسائط للمالك الجديد، دون إعادة إسناد الملكية تلقائيًا.

## إعدادات يدوية لم تُنفّذ

Firebase Functions params:

| الاسم | النوع | القيمة المطلوبة |
| --- | --- | --- |
| `BOOKING_CLOUDINARY_CLOUD_NAME` | String | اسم بيئة Cloudinary الموجودة المراد إعادة استخدامها |
| `BOOKING_CLOUDINARY_API_KEY` | Secret | مفتاح خادمي للحساب |
| `BOOKING_CLOUDINARY_API_SECRET` | Secret | سر خادمي للحساب |
| `BOOKING_WORKER_SECRET` | Secret | قيمة عشوائية قوية، تطابق سر Worker |
| `BOOKING_IMAGE_PROXY_URL` | String | عنوان HTTPS النهائي لوظيفة bookingImage في نفس البيئة |
| `BOOKING_WORKER_URL` | String | عنوان Worker نفسه في نفس البيئة، دون path إضافي |

Worker:

- أضف binding `BOOKINGS_BUCKET` لحاوية خاصة مستقلة؛ عطّل r2.dev وأي custom public domain لها. لا تغير `REELS_BUCKET` أو `R2_PUBLIC_BASE_URL` أو حاوية الريلز. توجد قطعة إعداد في `cloudflare/reels-worker/bookings.bindings.example.jsonc`، وليست ملف نشر صالحًا بمفردها.
- أضف `BOOKING_VIDEO_BRIDGE_URL` عنوان HTTPS للوظيفة في نفس مشروع Firebase، وWrangler secret باسم `BOOKING_WORKER_SECRET` بالقيمة المطابقة. تبقى إعدادات Firebase الأصلية الخاصة بالـWorker لازمة للقراءة؛ لا تُضع أسرار Service Account في vars أو Flutter.
- تحقق من صلاحيات حساب الخدمة الحالي لقراءة users وbooking_venues وbooking_media_reviews، ومن صلاحيات Functions لإدارة Firebase Auth وFirestore وSecret Manager وStorage القديم. لا تمنح إدارة حساب Cloudflare للعميل.
- فعّل فهرس `booking_media_reviews(venueId, ownerId)` عند نشر بيئة الاختبار. راقب `delete_pending`, attempts وlastError والسجلات القديمة المحتفظ بها. حذف الملفات ليس فوريًا؛ الحالة تمنع العرض الجديد مباشرة وتنتظر الحذف المادي.
- لم تُختبر قيم الحسابات أو سياسات Cloudinary الفعلية أو صلاحيات Cloudflare أو نشر bindings. لم يُنشأ bucket ولم يُشغّل اشتراك أو خدمة مدفوعة. أي نشر أو إنشاء موارد أو تغيير فوترة يحتاج موافقة منفصلة.

## الاختبارات وحدود التحقق

الأوامر المعتادة على جهاز تطوير له الصلاحيات:

```text
node --test functions/booking_media_policy.test.js cloudflare/reels-worker/test/bookings.test.mjs
firebase emulators:exec --only firestore,storage --project demo-aqar --config firebase.bookings-local.json "node test/run_booking_tests.cjs"
flutter test test/booking_widgets_test.dart test/booking_banners_test.dart test/booking_media_service_test.dart
flutter analyze lib/bookings lib/banners/banner_service.dart lib/screens/admin/add_banner_screen.dart
```

الاختبارات الجديدة تحاكي Cloudinary وطلبات Worker، ولا تتصل بمزودي الإنتاج. اختبارات التكامل تتطلب `demo-aqar` وFirestore على 127.0.0.1:8185، وتمنع التشغيل على الإنتاج. تحت قيود التشغيل المحلية استُخدم Node `--test-isolation=none`، وFirestore jar مباشر بلغة Java إنجليزية، وتجميع frontend_server وflutter_tester مباشرة مع suite harness يشغّل الاختبارات نفسها. تعذر تشغيل Flutter CLI المعتاد ومحلله الكامل بسبب منع إنشاء العمليات الفرعية؛ تجميع Dart الكامل ليس بديلًا عن كل فحوص lint.

التحقق المحلي لا يشمل رفعًا حقيقيًا إلى Cloudinary أو R2، أو نشرًا، أو تطبيقًا على Android/iOS، أو سياسات IAM أو codecs فعلية. معاينة فيديو pending تعتمد على دعم منصة video_player لهيدر Authorization؛ المعاينة على Flutter Web تحتاج تحققًا منفصلًا لأن دعم هيدرات الفيديو في المتصفح محدود. لا تعلن جاهزية الإنتاج قبل اختبار ذلك على المنصات المستهدفة.

التنظيف الحالي يقرأ سجلات v2 ثم يعالج حتى 50 ملفًا في دورة مع ميزانية زمنية؛ يجب مراقبة حجم المجموعة وتقييم pagination والفهارس والاستعلامات عند التوسع. بوابة الصور تستهلك تنزيلات ووقت Functions؛ لا يوجد ادعاء بأن التحويل يلغي متطلبات Blaze أو تكاليف Functions.

المراجع الرسمية: [Cloudinary Upload API](https://cloudinary.com/documentation/image_upload_api_reference)، [Authenticated media](https://cloudinary.com/documentation/control_access_to_media)، [Delivery signatures](https://cloudinary.com/documentation/delivery_url_signatures)، [R2 Workers API](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/).

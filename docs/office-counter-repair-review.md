# Approved office counter repair review

Definitions follow current public UI/model: approved office properties; active follower relationships (legacy missing isActive=true); published reviews (legacy missing status=published), rating parsed and clamped 1–5 as OfficeReviewModel. The dry-run found no duplicate active follower UID/office pairs or invalid isActive types.

| Export | Trigger / event | Relevant changes | Normal relevant-event reads / writes | Irrelevant-event reads / writes |
|---|---|---|---|---|
| refreshOfficePropertyMetrics | properties/{propertyId}, written | approved membership or office association | ledger+1 office: 2 reads; office+ledger: 2 writes; transfer ≤3/3 | 0/0 for views, description, unrelated edits |
| refreshOfficeFollowerMetrics | office_followers/{followerId}, written | active membership or office association | 2/2; transfer ≤3/3 | 0/0 for name/photo/updatedAt |
| refreshOfficeReviewMetrics | office_reviews/{reviewId}, written | published membership, normalized rating or office association | 2/2; transfer ≤3/3 | 0/0 for comment/owner reply |

Each source write still invokes its document-written trigger; Firebase does not offer field-change filtering on these triggers. Early exit performs no Firestore operation for irrelevant changes. No full source query or scan occurs in any handler. Functions write only offices and private office_counter_events, neither of which triggers these three Functions, so no recursive loop. Deleted offices are never recreated. Inactive/blocked existing office counters remain current for later restoration; visibility remains controlled by existing status/block logic.

Idempotency: server CloudEvent ID+kind SHA256 ledger and all affected office updates commit in one Firestore transaction. Concurrent duplicate delivery can apply only once. Distinct event deltas commute, including deletes and office transfers. Internal officeCounterTotals preserve signed intermediate deltas and rating sums; public counts clamp only display values to zero. An old client updating public summaries does not change the canonical totals used for the next transition. Timestamp comparison uses Firestore's microsecond precision. Deleted source snapshots use CloudEvent time rather than the old document updateTime.

Retry=true is required for a temporarily failed atomic counter transaction and for relevant events waiting for the initial baseline. Retry=false can permanently lose a follow/approval during a transient failure. No automatic callable/polling/heartbeat is introduced. Old offices missing the approved baseline temporarily retry until bounded backfill completes. Unrecognized/malformed association IDs are excluded before I/O. Persistent invalid baseline metadata requires intervention and is monitored; it must not be hidden or retried experimentally.

Deployment scope: exactly the three named exports, Node24, us-central1, timeout30s, maxInstances3, retry enabled. If Firebase requires retry acknowledgement, --force applies only to this exact three-function --only scope; no general --force and no unrelated deploy. No Rules/manual IAM/App Check change.

Backfill dry-run: 2 offices, 35 source documents, 39 returned document reads including office reads, 2 planned summary writes, zero writes performed. First office: 13 properties, 11 active followers, 5 published reviews, rating5. Second: 0 properties, 4 active followers among 5 records, 1 published review, rating5. Counter initialization scans only these office-scoped source sets once in 100-document cursor pages. Logical old-value snapshot is taken before writes. Maximum scope safeguards: 50 offices, 5000 source records per query; no source/document deletion or source rewrite.

Concurrency: deploy all three triggers first; initial old-office events retry until baseline. Backfill fixes the server readTime from the office read and uses that same readTime explicitly on every paginated source query. Its office updateTime write precondition detects concurrent counter writes and causes at most five repair attempts. A source change after cutoff either updates the office before commit (precondition rejects and recomputes) or is applied by its queued event after the baseline commit. The commit writes summary fields/canonical totals/version/cutoff only. Trigger revisions <= cutoff are already included and do not apply; later events apply their delta exactly once. Re-running initialization takes a newer consistent snapshot, so ledger events do not double count. Offices created during deployment are recaptured after all triggers are ACTIVE. Later new offices initialize from createTime and zero source contribution, relying on office creation preceding valid child actions in the application. An existing office without baseline never silently initializes to zero.

Rollback snapshot stores only old office summary fields and absent-field list, no source user content. Counter Functions were absent before repair; exact rollback would disable/delete only the newly created three Functions and conditionally restore only approved summary fields from snapshot, preserving source records and Presence Functions. No rollback performed automatically without a proven unsafe incident. Logs/configuration/reconciliation are checked before switching client cards to summaries.

Tests cover zero-I/O irrelevant edits, creation/approval/rejection/pending/restoration/deletion, association removal, transfers, concurrent duplicates, follow/unfollow/deletion, reverse event order, legacy defaults, rating edit/hide/transfer, snapshot cutoff, nanosecond normalization, deleted/inactive office, public-summary tampering resilience and events crossing backfill cutoff. Presence authorization regression runs alongside counter tests. Production transitions use emulator tests, not fake public properties or edits to real source accounts.

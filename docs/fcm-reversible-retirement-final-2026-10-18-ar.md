## فصل Git: غير ضروري لهذا المسار

يبقى مشروع `notification-server` مرتبطًا بـ`aysar93/notification_server` وفرع الإنتاج `main`. لا deploy hooks في القائمة الحالية. البديل الأدنى هو تغيير **Ignored Build Step** لهذا المشروع من الإعداد الحالي null إلى `exit 0` / «Don't build anything». وفق Vercel، يلغى البناء عند خروج الأمر بـ0؛ هذا لا يستبدل النشر الجاري أو نسخة الصيانة. يبقى Git متصلًا وتبقى إمكانية استئناف البناء مستقبلًا. [إعدادات البناء](https://vercel.com/docs/project-configuration/project-settings).

الأثر: تتوقف الأبنية الآلية المستقبلية لهذا المشروع، بما فيها Preview؛ وقد تُحتسب محاولات البناء الملغاة ضمن حصص النشر. يمكن للمخول تجاوز Ignored Build Step عند إعادة نشر يدوية، ولذلك ليس حاجز IAM ضد المالك؛ يلزم اعتماد المصدر اليدوي ومنع ترقية مرسل قديم إلى النطاق القانوني ضمن سياسة التشغيل. لا أدعي أن ملف إعداد أو حارس محلي يمنع المالك من تجاوز السياسة.

- `notification-server-git-main-aysar93s-projects.vercel.app`

الإجراء المقترح Deny لكل المسارات والطرق على هذه الأسماء فقط، لتفادي حصر الحماية في تهجئة /send واحدة. لا wildcard أو نطاق فريق كامل أو شرط IP أو تغيير DNS/alias. النطاق القانوني ورابطا الخادم الجديد والصيانة غير مدرجين. تدعم Vercel مطابقة hostname وإجراء Deny. [مرجع Firewall](https://vercel.com/docs/vercel-firewall/vercel-waf/rule-configuration).

**حدّ مهم:** Firewall الحالي disabled، وقواعده المخصصة صفر، ولا draft ظاهر وقت القراءة. إذن النشر المستقبلي يحتاج تفعيل Firewall للقاعدة المحددة فقط؛ لا نشغّل bot challenge أو قواعد managed أو ننشر draft آخر. ملف المرشح محلي، ولم ننشئ حتى draft إنتاجيًا. ثبوت سلوك القاعدة على المنصة يحتاج تحققًا محدودًا بعد الموافقة، ولا يُستبدل بفحص JSON محلي.

خطة التنفيذ المعروضة، **كلها تحتاج موافقة إنتاجية مستقلة**:

1. إعادة قراءة revision وإعداد البناء وdrafts/aliases قبل التغيير؛ توقف عند تغير غير متوقع. حفظ baseline آمن.
2. ضبط Ignored Build Step فقط مع إبقاء Git متصلًا. عدم نشر كود أو ترقية أي deployment.
3. تفعيل القاعدة المحددة أولًا بإجراء Log إن لزم رصد طلبات حقيقية مدة أطول دون حجبها؛ ثم Deny بعد مراجعة النتيجة. Log ليس تعطيلًا ولا يجيز رفع علم تنسيق المداخل.
4. عند Deny، وضعها قبل أي bypass مخصص والتحقق من استبعاد كل bypass ذي صلة؛ الحماية القائمة من Vercel Authentication لا تعادل إثبات منع bypass للـWAF. ظهور bypass غير قابل للحصر يوقف إعلان اكتمال التقاعد.
5. تحقق جديد ضيق: GET على الأسماء المحظورة، وقراءة جاهزية النطاق القانوني والصيانة لأن إعداد Firewall تغير؛ لا POST /send قديم، ولا اختبار إشعار أو جهاز أو حمل. بعدها حارس `--reversible` بأدلة فعلية؛ يقبل بقاء النشرين ويتطلب إثبات الحظر والقوائم الفارغة وعدم صلاحية الإرسال.

**التراجع:** تعطيل القاعدة المسماة وحدها ونشر diff مراجع، فيعود الوصول إلى الروابط القديمة وفق حماية Vercel السابقة، دون إعادة إنشاء النشرين. يرجع enabled=false فقط إذا لم تُضف إعدادات أخرى تعتمد عليه؛ لا استعادة config كامل تمحو تغييرات متزامنة. خلل خدمة الخادم الحالي يعالج بترقية نسخة الصيانة المتوقفة. إعادة إعداد البناء السابق ممكنة لكنها تعيد خطر النشر الآلي القديم، فلا تُنفذ كجزء تلقائي من تراجع خدمة. لا حذف أو فصل Git أو إبطال مفتاح في هذه الخطة.

قاعدة hostname تغطي العناوين المجرودة فقط. إنشاء alias جديد أو ترقية نشر قديم إلى النطاق القانوني بواسطة مالك مخول يحتاج منعًا تشغيليًا ومراجعة؛ لا ندعي حظرًا مطلقًا ضد صلاحيات المالك.

## الحل الخادمي للتعليقات والردود دون تحديث التطبيق

المسار المتوافق هو الاعتماد على **إنشاء المصدر الحقيقي** في `properties/{propertyId}/comments/{commentId}` و`.../replies/{replyId}`، لا استنتاج المصدر من نص إشعار قديم. الخادم يملك معرّف المصدر من الحدث حتى لو لم تضمه كتابة العميل إلى notifications. ثم يتحقق من هوية الكاتب الموثقة وملف حسابه وصاحب العقار/التعليق، ويشتق المستلم والهوية canonical ويحفظ صندوقه ويمر عبر claims/cohort القائمة. هذا الأساس قائم ومختبر سابقًا؛ لم نكرر اختباره.

ظهر نقص محدد في مسار التحقق المباشر غير الإداري: وجود المصدر وعلاقة مؤلفه لا يستبعدان كل حالات إخفائه/حذفه أو إخفاء التعليق الأب للرد. جُهز overlay معزول في `server-candidates/legacy-source-validation/` يستبعد هذه الحالات ويحافظ على اشتقاق المستلم من المستندات. لا يغير كتابات التطبيق أو القواعد أو هوية الحدث أو مسار الإدارة الموثوق، ولا يضيف إرسالًا أو صلاحية. مرشح تعديل ثلاث دوال فقط مستقبلًا: `deliverBridgeNotification` و`bridgeCommentCreated` و`bridgeReplyCreated`؛ لم ينشر أي منها الآن، وباقي الخمس لا تحتاج تعديلًا لهذه العلة.

نجح فحصان جديدان لسياسة التفويض/الإخفاء، وفحص تركيب adapter. ونجح فحصان لوضع التقاعد القابل للتراجع وحصر hostname؛ **4 اختبارات جديدة إجمالًا**، بلا مزود أو شبكة إرسال. لا إعادة لاختبارات القواعد/الأجهزة/CI السابقة. الـoverlay ليس bundle جاهزًا للنشر المباشر، واختبارات السياسة ليست شهادة اختبار جهاز جديد.

**المخاطرة الباقية لا أخفيها:** هذا يؤمّن مصدر Push ويتيح التحقق الخادمي مع استمرار التعليقات والردود القديمة، لكنه لا يمنع القبول الأولي لكل مستند صندوق مزور تحت قواعد الإنشاء القديمة. كما أن ربط مستند قديم بمصدر باستخدام الوقت/النص تخمينًا قد يخلط أحداثًا متزامنة؛ لم أضف هذا المسار أو حذفًا آليًا. التنقية بعد الكتابة قد تقلل المخاطرة لكنها لا تضمن عدم ظهور المستند مؤقتًا. قواعد مشددة ترفض بعض الكتابات القديمة لم تُطبق ولن تُعرض كحل متوافق.

لذلك يمكن الحفاظ على النسخ القديمة والتحضير لتشغيل FCM من المصادر الموثقة، مع مخاطرة صندوق قديم معلنة تحتاج قرارًا مستقلًا قبل GO شامل. ضمان منع الإنشاء المزور لحظة حدوثه، مع قبول شكل الكتابة القديم نفسه دائمًا، ما زال غير مثبت تحت العقد الحالي. هذا ليس سببًا لحذف النشرين أو إعادة اختبارات ناجحة، ولا موافقة ضمنية على مخاطرة الصندوق.

**المتبقي:** موافقة محددة على إعداد البناء وقاعدة الحظر القابلة للتراجع عند اختيار تنفيذها، ومراجعة/اعتماد نشر إصلاح المصدر المحدود، وحسم سياسة مخاطرة إنشاء الصندوق القديم. تفعيل مجموعة وصلاحية إرسال ومرشح canary ما زالت موافقات لاحقة منفصلة. لا تدخل أجهزة أو تسجيل دخول أو أسرار مطلوب الآن.

## الموانع وطريقة إغلاقها

### 1. إعداد النشر الافتراضي ما زال يتضمن تشديداً مؤجلاً غير متوافق

`firebase.json` يشير إلى `firestore.rules`. ذلك الملف يتطلب `validPushSource` لكل إنشاء في المجموعة القديمة، ويعتمد على حقول مصدر مثل commentId/replyId/messageId لا توفرها بعض النسخ المنشورة. هذا هو التشديد الذي تقرر عدم تطبيقه على الإنتاج. كما أن المصدر الافتراضي `functions` يصدر دوال FCM والجسر من index العام، بينما نشر الإنتاج المعتمد تم بحزمة مستقلة `push-bridge` وبنطاق ثماني دوال محدد.

**الأثر الدقيق:** merge لا ينشر القواعد أو الدوال تلقائياً وفق ملفات GitHub Actions المقروءة. الخلل هو أن main المقترح سيحمل إعداد نشر افتراضياً لا يمثل قرار التوافق وحزمة النشر الإنتاجية المعتمدة؛ نشره لاحقاً بالأمر المعتاد قد يشدّد كتابات النسخ القديمة أو يتجاوز نطاق الدوال الثماني.

**الإغلاق:** فصل المرشحات المؤجلة عن إعداد النشر الافتراضي، وجعل إعدادات المصدر المسجلة في Git تطابق الفصل المعتمد بين الدوال القائمة وحزمة الإشعارات، مع إبقاء قواعد المجموعة القديمة المعتمدة دون تشديد. يكفي تحقق جديد من إعدادات النطاق والتوافق المتأثرة؛ لا إعادة اختبارات الأجهزة الناجحة. لا تغيير لقواعد الإنتاج خلال هذا الإصلاح المحلي.

### 2. آخر التحضيرات غير مرفوعة، واختبارات الصندوق غير موصولة بـCI

الـcommits المحلية السبعة، ومنها 8ee5fb4، غير موجودة في رأس GitHub. لا تذكر ملفات workflow الحالية `trusted_inbox_next.test.cjs` أو `trusted_inbox_history_plan.test.cjs`؛ لذلك لا توجد تغطية CI مسجلة لهذين التعديلين حتى لو نجحت الاختبارات القديمة. واجهتا GitHub المستعملتان أعادتا workflow_runs=[] وstatuses=[] للرأس البعيد؛ الأولى تعرض تشغيلات pull_request فقط والثانية حالات commits، فلا أستنتج من ذلك فشل كل CI أو عدم وجود تشغيلات push سابقة.

**الإغلاق:** إضافة مهمة محددة للاختبارات الجديدة والحزمة المستقبلية فقط، مع استخدام مشروع demo والمحاكي والمنفذ المطلوبين؛ رفع رأس المراجعة بعد التحقق من مشغلات البناء؛ ثم توثيق نجاح التحقق الجديد على الرأس المرفوع. تعديل وجهة PR أو إعداد PR تجميعي إلى main بعد مراجعة الفارق الكامل. لا حاجة لإعادة السيناريوهات السابقة غير المتأثرة.

### 3. حدود الوسائط والنشر الخارجي تحتاج حسم دمج

الفارق الحالي يتضمن حراس عزل قديمة في `lib/services/cloudinary_service.dart` و`lib/chat/services/chat_audio_service.dart` و`lib/reels/services/reel_service.dart`. هذه الإضافات لا تنفذ عند تعطيل FCM_MIGRATION، وليست دليلاً على عطل وسائط إنتاجي، لكنها تدخل في دمج الحزمة الكاملة رغم شرط فصل عمل الوسائط. لم تُعدّل هذه الملفات في هذه المراجعة.

**الإغلاق:** مراجعة/فصل هذه الإضافات القديمة في حزمة الدمج دون تغيير عمل مشروع نقل الوسائط أو نسخ تعديلاته. فحص أي فرع وسائط مطلوب دمجه يتم على مرجعه المحدد؛ لا يُستنتج عدم وجود تعارض مع عمل غير منشور من نجاح merge-tree مع main الحالي.

GitHub Actions المقروءة تبني وتختبر دون أمر نشر Firebase/Vercel أو رفع متجر. لكن `codemagic.yaml` يتضمن workflow منفصلاً `ios-app-store` مع نشر إلى App Store Connect؛ لا توجد triggering في YAML المقروء. هذا لا يثبت وحده حالة تشغيلات/webhooks لوحة Codemagic أو تكاملات GitHub الخارجية. قبل رفع/دمج الحزمة يلزم تحقق قراءة فقط من المشغلات ذات الصلة لضمان عدم تشغيل النشر؛ لا تعطيل خدمات أو تعديل إعدادات إنتاجية تلقائياً.

## الإجابات المباشرة

1. لا تعارض نصياً مع main الحالي ولا خطأ جديد مثبت في الصندوق نفسه؛ الموانع في إعدادات الدمج/النشر وتغطية التغييرات الأخيرة وحدود النطاق كما سبق.
2. Git merge وحده لا يغيّر التطبيقات المثبتة أو Firebase أو Vercel. لا أضمن غياب أثر من تكامل خارجي غير مفحوص، والقواعد الموجودة في حزمة الدمج غير مناسبة لنشرها كما هي.
3. الصندوق الجديد اختياري ومعطل افتراضياً؛ paused والقوائم الفارغة وغياب إذن الإرسال تبقى حدود الإنتاج المعتمدة. سلامة الإرسال المتوقف لا تجعل قواعد الكتابة غير المتوافقة مناسبة للنشر.
4. جميع commits FCM المذكورة محفوظة محلياً؛ آخر سبعة ليست على GitHub وقت الفحص. تقرير هذه المراجعة سيُحفظ محلياً أيضاً. لم أدفع فرعاً يمكنه تشغيل بناء تلقائي دون تحقق حدود النشر.
5. يمكن فصل دمج الكود عن تحديث المتاجر تقنياً، لكن لا أوصي بدمج هذه الحزمة كما هي قبل إغلاق الموانع أعلاه. الدمج ليس شرطاً لتفعيل FCM الخادمي، وتفعيله غير مأذون في هذه الجولة.

سبب عدم الدمج سابقاً كان تعليمات عدم الدمج الصريحة، والتحضير المحلي دون نشر. التفويض الحالي مشروط بالسلامة الكاملة؛ لم يتحقق هذا الشرط للحزمة الحالية، لذلك بقي main والإنتاج دون تغيير.

## المراحل التالية ومعايير الإغلاق

1. مراجعة المستخدم للصور واتجاه التنظيم، ثم استكمال التفاصيل الغنية والوسائط والمرافق، ونقل تخطيطات الطلب والدفع والمالك والإدارة إلى جميع التدفقات الفعلية. القبول: صور من الشاشات الفعلية لكل دور مع حالات تحميل وفراغ وخطأ ونص كبير، ثم موافقة المستخدم. عمل هذه الدفعة قابل للتعديل على الفرع التجريبي.
2. بناء Android staging مطابق للـcommit، والتحقق من projectId قبل أي تثبيت أو اتصال. تنفيذ warm-cache ثم offline ثم تبديل حساب وسحب دور مع أدلة عدم ظهور الهاتف/المرجع المالي في أي frame، مع رفض قراءة الخادم للحساب غير المصرح. المكونات الحالية بداية لهذا القبول وليست نهايته.
3. سباق عميلين/واجهتين للحجز وإقرار العربون والاسترداد والتسوية. القبول: نتيجة واحدة صحيحة ودفتر وتدقيق بلا تكرار، وواجهة كل طرف تتعافى من الرد المتأخر أو الضائع.
4. حقن نوافذ الشبكة الدقيقة وdiscard المطول مع إثبات زمن بداية الفشل والمهلة والتنظيف وعدم بقاء أجزاء بعد تحقق الخادم. لا تختصر مهل الأمان لتسهيل الاختبار.
5. مراجعة مخططات مالية قديمة بعينات مجهولة الهوية ومعاني حقول معتمدة. الرفض الآمن الحالي يبقى إلى أن تثبت سلامة التحويل؛ لا ترحيل إنتاج ضمن المهمة.
6. قبول الأجهزة والمنصات المتوفرة فعليًا، ثم قرار Android وiOS منفصل. لا يثبت نجاح Web أو Flutter test قبول فيديو العتاد أو APNs أو أذونات iOS.

النشر إلى Firebase لم يكن مطلوبًا لهذه الدفعة: لم يتغير كود دالة أو Rules منشورة، ولذلك لم تُنشر وظائف أو قواعد. لم يُمس main أو aqar-9f3f9 أو المتاجر أو الفوترة، ولم تُنفذ دفعات أو ترحيلات حقيقية. fixtures الجديدة كانت في المحاكي فقط وأُغلق بعد نجاح الاختبارات. بالإضافة إلى ذلك نُظفت بقايا المحاولة السابقة على staging بعد مطابقة projectId وعلامات الاختبار الاصطناعية: سجل دفتر واحد وحجز اصطناعي واحد وأربعة تنبيهات مرتبطة. ثبت 404 للسجلين ونتائج خالية لاستعلامات الدفتر والتدقيق والتنبيهات الخاصة بهما. لم تتغير صلاحيات حسابات staging. الموافقة المطلوبة الآن على اتجاه التصميم؛ لا توجد مطالبة بموافقة نشر أو تشغيل إنتاج.

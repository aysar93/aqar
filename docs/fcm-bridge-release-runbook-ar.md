# خطة طرح وتراجع جسر الإشعارات

هذه خطة قابلة للمراجعة، وليست إذنًا بالنشر. يبقى الإنتاج وVercel والمتاجر وOneSignal كما هي إلى موافقة منفصلة. القرار والأدلة في [تقرير التحقق](fcm-bridge-validation-2026-10-16-ar.md).

## بوابات ما قبل الإنتاج

1. تطبيق OneSignal تجريبي منفصل له إرسال متاح: ربط FCM وOneSignal للتثبيت نفسه، ثم جهاز ثانٍ للحساب، وتبديل الحساب والخروج والتراجع وتكرار الحدث. لا تستخدم تطبيق OneSignal الإنتاج أو خطة مدفوعة لهذا الاختبار.
2. Vercel Preview منفصل يستخدم `aqar-fcm-test-20261014` فقط وحساب خدمة محدودًا له. الحزمة المعزولة تُجهز بواسطة `tools/build_push_bridge_preview.cjs` وتمنع project/credential mismatch. لا تنسخ `.env` الإنتاج. اختبر HTTP بدون مصادقة: لا هوية = 400، حدث غير مثبت = 202 دون إرسال، حدث مثبت = ledger مشترك، payload زائد = 413، كثافة غير مقبولة = 429، وفشل داخلي = 503 عام دون أسرار.
3. معالجة اعتماد خادم Vercel المتعقب: حدد الخدمة والاعتماد من دون نشر قيمته، دوّر الاعتماد ضمن إجراء إنتاج مخول، خزّن البديل في Secret Manager/متغير خادم فقط، أزل الملف من التتبع وأضف التجاهل. حذف الملف في commit جديد لا يمحو التاريخ؛ راجع الوصول والتاريخ، ولا تعيد كتابة تاريخ Git المشترك تلقائيًا. لا يكفي تدقيق npm لمعالجة تسرب اعتماد.
4. مراجعة قواعد صندوق الإشعارات القديمة مع نسخة منشورة فعلية؛ لا تعتمد على غياب `pushTransport` لإثبات صلاحية المرسل. حدد أثر تشديد القواعد على الإصدارات القديمة، وأثبت البديل الخادمي قبل قطعها.
5. نسخة متجر Android ونسخة App Store قديمة: إثبات الاستقبال والنقر في الحالات الثلاث بإذن اختبار إنتاج ضيق لاحق. وجود SDK أو قبول FCM لا يثبت نجاح النسخة المثبتة. لا تستخدم مرشح الإنتاج في الاختبار التجريبي لأن تشغيله يتصل بإنتاج Firebase.
6. سياسة احتفاظ بسجلات الجهاز والـ ledger، مراقبة الفواتير الفعلية، ومستوى خدمة مقبول للفشل والتأخير؛ لا تعامل تنبيه 5 دولارات أو maxInstances كسقف مالي.

## التنسيق قبل إرسال أول حدث إنتاج

احفظ مراجع نشر Vercel والدوال والقواعد وإعداد rollout السابق وأرقام النسخ. راجع مطابقة Firebase وAPNs والشهادات. يجب أن يستخدم HTTP وtriggers سجل المطالبات نفسه قبل ضبط `legacyIngressCoordinated=true`؛ لا يُضبط هذا الحارس لمجرد نجاح نشر خدمة منفردة. أبقِ المزودين منفصلين لكل تثبيت، ولا تنشئ FCM recovery approval من حقل عام تلقائيًا.

لكل جهاز قديم مرشح للاستعادة: إثبات وصول خاص بالجهاز وتسجيل دخول الحساب الحالي، وتوثيق موافقة المشغّل على UID وبصمة الرمز ومدة قصيرة محددة. لا تُدرج الرمز الخام في تقرير أو issue. إن فشل إثبات الملكية أو صلاحية الرمز، يحتاج الجهاز تحديثًا أو إعادة تسجيل؛ لا تعمم نتيجة جهاز واحد على كل أجهزة الحساب.

## مراحل الطرح المقترحة بعد الموافقة

ابدأ بقائمة تثبيتات اختبار صريحة، ثم 1%، 5%، 25%، 100%. راقب كل مرحلة مدة لا تقل عن 24 ساعة وتحقق يدويًا من عينة Android وiPhone قبل الانتقال؛ هذه سياسة مقترحة قابلة للتعديل وفق حجم الاستخدام. لا تتوسع مع أي تسرب بين الحسابات أو تكرار مثبت أو إرسال معلق غير مفسر. قارن فشل المزود والتأخير بخط أساس متفق عليه، وأثبت أن التنبيهات تصل للمسؤول وأن الفاتورة متاحة للمراجعة.

لا ترسل حدث اختبار حساسًا إلى جمهور كامل. إشعار عام لا يحتاج وجهة تفصيلية يفتح صندوق الإشعارات؛ هذا سلوك متوقع، وليس فشل توجيه إلى عقار.

## التراجع

عند خطر تكرار أو خلط حسابات: أوقف cohort أو اختر `paused` من إعداد الخادم المحمي. لا تحذف ledger ولا تعيد إرسال `attempting` أو `review_required` تلقائيًا؛ قد يكون المزود قبل الرسالة قبل فقد التأكيد. إصلاح سباق التراجع يعيد قراءة الإعداد داخل معاملة الحجز، لكن رسالة قُبلت عند المزود قبل الإيقاف لا يمكن سحبها بهذا الحارس.

إرجاع النقل إلى OneSignal مشروط بكون Mobile Push متاحًا فعليًا. طالما هو متوقف بسبب MAU، فهذا ليس مسار استعادة مضمونًا؛ تبقى الأجهزة ذات FCM المثبت ضمن المسار المخول، وصندوق الإشعارات داخل التطبيق بديلًا للأجهزة الأخرى. لا تُنشّط دفعًا ثانيًا على الجهاز نفسه لمحاولة تعويض فشل ملتبس. أعد نشر النسخة السابقة فقط ضمن إجراء مخول، مع الاحتفاظ بسجلات الهوية والمطالبات اللازمة لمنع التكرار.

لا تحذف مفاتيح APNs أو شهادات التوقيع أو توقف OneSignal بسبب نجاح cohort جديدة. إغلاق المزود القديم يتطلب جرد تغطية حسب الجهاز، واختبار نسخة المتجر، وخطة واضحة للأجهزة التي لم تحدث، وموافقة المستخدم النهائية.
